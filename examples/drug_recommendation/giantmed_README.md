# GiantMed with SafeDrug

`giantmed_mimic3.py` trains SafeDrug for one epoch on the repository's MIMIC-III demo and evaluates the backbone and GiantMed. Run it from the repository root:

```sh
python examples/drug_recommendation/giantmed_mimic3.py --model Qwen/Qwen3-8B
```

This is a pipeline smoke test, not a meaningful performance comparison or a reproduction of the paper. SafeDrug is trained for only one epoch on a tiny demo, leaving 121–123 medications per visit in the boundary in the recorded five-visit run; its baseline recommended about 59 medications per visit. Access to cached or downloadable PyHealth medical-code resources and an LLM is needed. Omitting `--model` uses a no-op response for a smoke test, so the two sets of metrics must match. `--demo-refinement` uses a deterministic fake responder to exercise score updates; its predictions have no clinical meaning. The example prints no patient prompts, but the LLM receives clinical information; use a backend appropriate for the dataset's access terms.

GiantMed is an inference postprocessor. Supply raw task samples from **training patients only**, model probabilities in the exact order of the label vocabulary, and a DDI matrix in the same order. The helper excludes a query's own patient from retrieval; callers must keep validation and test patients out of the training index. Like the reference, retrieval may return zero-similarity visits when there is no diagnosis overlap; callers should consider this when interpreting evidence. Inputs should contain `patient_id`, `visit_id`, `conditions`, `procedures`, `drugs_hist` and, for retrieved training examples, `drugs`. The query's current `drugs` target is never put in the prompt. The returned tuple contains the revised vector and prompt; a missing, invalid or duplicated response leaves the corresponding original score in place. Use `refine_with_details` to inspect candidate, accepted and changed score counts and detect invalid or partial responses. Numeric scores or numeric strings directly keyed by ATC code and a single nested `probability` field are accepted, including a JSON object surrounded by prose or a closed thinking block. The reference tuple format is not parsed. A valid JSON response with no accepted scores has status `no_updates`. Medication codes must be nonempty strings; all-digit codes are rejected in batched mode to avoid index ambiguity. The example reports these counts without printing patient prompts.

The reference uses diagnosis Jaccard similarity, top three training visits, a 0.3 to 0.7 boundary and DDI evidence among boundary candidates. This implementation defaults to a half-open boundary `[0.3, 0.7)`, as in the reference refinement script; set `upper_inclusive=True` to follow the paper’s closed interval. The prompt uses shared clinical guidance across modes, while its compact wording, code/index keyed JSON output, candidate ordering and displayed precision differ from the reference name-based tuple format. Budgeted prompts also differ in layout and may omit supporting evidence. The reference also filters retrieved drug evidence with MEDI and NDC/RxCUI mappings, with a previous-visit rescue. `MediEvidenceFilter.from_reference_files` prepares the filter from MEDI.csv, NDC-to-RxCUI and RxCUI-to-ATC files, a clinical ingredient cache, and the MIMIC-III prescription table, indexing training visits only. To enable it in the example supply `--medi`, `--ndc-rxcui`, `--ndc-atc`, and `--ingredient-cache` together; otherwise the example reports that the filter is disabled. These source files must be obtained or prepared separately. The example builds MEDI index keys with the same PyHealth NDC-to-ATC3 mapper used for task labels; the default `from_reference_files` behavior instead uses the reference RxCUI-to-ATC mapping unless `ndc_to_atc3` is supplied. Missing keys are reported separately from missing ingredients and MEDI indication mismatches; history rescue takes precedence. The external RxCUI ingredient cache is incomplete, so missing ingredients can still suppress valid evidence. A DDI prompt is not a hard constraint.

The demo's cached PyHealth NDC-to-ATC mapping also contains an over-broad entry: NDC `60258000601` maps to 133 ATC codes across 52 ATC3 labels. Its external RxCUI is a non-current proprietary placeholder without a reliable ingredient mapping. This can inflate the demo label vocabulary and affect retrieval, predictions and metrics. The recorded five-visit results should be treated as exploratory until the mapping is corrected and the experiment repeated.

PyHealth's split-aware task processing fits input processors on training patients, but its label processor adds labels found in held-out data; a benchmark intended to avoid that vocabulary exposure should provide a prespecified medication vocabulary. Reproducing the paper additionally requires its cohort construction, train/validation/test splits, medication vocabulary, mappings, model checkpoints, LLM setup and evaluation protocol. The example uses a freshly trained PyHealth model and does not claim numerical parity.

The example uses a 0.5 decision threshold and averages visit metrics within each patient, then across patients, as in the released script. The DDI rate pools medication pairs across visits. The example records a per-visit `refinement_error` and retains backbone scores if prompt construction or generation fails; the printed error should be investigated before interpreting aggregate metrics. The reference generation defaults to temperature 0.6 and 4096 new tokens, while the paper reports temperature 0.7 and a 4096-token input limit. For a selected model or supplied prompt tokenizer, the example fits prompts to 4,096 input tokens by default using the tokenizer and a 256-token reserve for provider formatting. The OpenRouter run stops if the provider reports a prompt above that limit. The paper and released script use different generation settings; configure and document them for experiments.

The public [MEDI-C download](https://www.vumc.org/wei-lab/medi) contains the columns used by the filter and is distributed under CC BY-NC-SA 3.0; obtain it separately and check its terms for your use. The reference ingredient cache is in the [GiantMed repository](https://github.com/lvhangkenn/GiantMed/tree/main/data/raw/MIMIC-III). The NDC-to-RxCUI and RxCUI-to-ATC files used for the demo check were `data/ndc2rxnorm_mapping.txt` and `data/ndc2atc_level4.csv` from [GAMENet](https://github.com/sjy1203/GAMENet/tree/master/data); these are external mappings and may differ from the authors' original versions.

For small hardware, `--max-test-visits` and `--max-new-tokens` limit a smoke run, and `--boundary-low` and `--boundary-high` can narrow the candidate set. Changing the boundary changes the method configuration and does not reproduce the paper. `--save-responses PATH` writes raw model responses locally for parsing diagnostics; responses can contain patient information and should be stored accordingly.

To use an OpenRouter model in the example, set `OPENROUTER_API_KEY` in your environment and pass `--openrouter-model qwen/qwen3-14b`. This transmits the current visit, prior medication history and retrieved training-visit evidence in each prompt to OpenRouter and its selected provider; check the dataset terms and provider's data handling before using it with real records. Do not put the key in command-line arguments or output files. API availability, routing and charges depend on the account and provider.

The input budget preserves the current visit and every candidate code and score. If necessary, it assigns fixed shares of remaining space to candidate names, interaction pairs, similar visits and medication history. Unused shares are not redistributed. Interaction pairs are ordered by candidate scores. Candidates are numbered rows of code, score and name; interactions use those row numbers in an adjacency list. Overlapping diagnoses and procedures use the codes already described in the current-visit section. Counts of retained and total names, history visits, similar visits and interaction pairs are printed for every visit. This ordering is a practical approximation and is not an interaction severity ranking; missing names or DDI pairs can materially change the model’s decisions. If the current visit and candidate scores alone exceed the budget, the run stops rather than silently truncating them. Supply `--prompt-tokenizer` for an OpenRouter model other than Qwen3-14B. Provider chat formatting can differ from the local tokenizer; verify reported usage.

### Candidate batching

With a tokenizer and input budget, pass `--candidate-batch-size 32` to refine at most 32 target drugs per request. Each request includes the current visit, every target's code, score and available name, plus the code, score and available name of each boundary drug that interacts with a target. Its indexed interaction list includes **all** boundary interaction pairs involving those targets, including cross-batch pairs. Context drugs are not updated by that request; each drug is updated only in its own target batch. Planning fails before generation if even one target and its complete interaction context cannot fit. The returned `prompt_budget` reports unique DDI coverage, cross-batch pairs, name resolution, per-request token counts and retained history and retrieved visits. `prompts` and `responses` contain all batch calls; the legacy `prompt` and `response` fields contain the first call. Batched responses use zero-based target row numbers as string keys; target ATC codes are also accepted, while out-of-batch and ambiguous duplicate updates are rejected. Indexed responses must contain the complete canonical set of target indices, with no extra numeric keys. Otherwise indexed scores fall back to the backbone because partial or one-based indices cannot be mapped reliably; unambiguous code-keyed scores can still be accepted.

Batching is an adaptation: the paper and reference use one prompt per visit. The batches are refined independently, so interaction evidence is not a hard constraint and independently produced decisions can still conflict. Similar visits are fitted before medication history in each batch; either may be truncated to fit. Each additional request can increase latency and API cost. If a response omits a target or returns an invalid score, the backbone score is retained for that target.

For OpenRouter debugging, `--response-trace PATH` writes each response incrementally as JSONL; this may include clinical information and must be stored accordingly.
