# GiantMed with SafeDrug

`giantmed_mimic3.py` trains SafeDrug for one epoch by default on the repository's MIMIC-III demo and evaluates the backbone and GiantMed. Run it from the repository root:

```sh
python examples/drug_recommendation/giantmed_mimic3.py --ndc-rxcui /path/to/ndc2rxnorm_mapping.txt --ndc-atc /path/to/ndc2atc_level4.csv --model Qwen/Qwen3-8B
```

This is a pipeline smoke test, not a meaningful performance comparison or a reproduction of the paper. SafeDrug is trained for only one epoch on a tiny demo. Access to cached or downloadable PyHealth medical-code resources is needed. An LLM is needed only for model-generated refinement. Omitting `--model` uses a no-op response for a smoke test, so the two sets of metrics must match. `--demo-refinement` uses a deterministic fake responder to exercise score updates; its predictions have no clinical meaning. The example prints no patient prompts, but the LLM receives clinical information; use a backend appropriate for the dataset's access terms.

GiantMed is an inference postprocessor. Supply raw task samples from **training patients only**, model probabilities in the exact order of the label vocabulary, and a DDI matrix in the same order. The helper excludes a query's own patient from retrieval; callers must keep validation and test patients out of the training index. Like the reference, retrieval may return zero-similarity visits when there is no diagnosis overlap; callers should consider this when interpreting evidence. Inputs should contain `patient_id`, `visit_id`, `conditions`, `procedures`, `drugs_hist` and, for retrieved training examples, `drugs`. The query's current `drugs` target is never put in the prompt. The returned tuple contains the revised vector and prompt; a missing, invalid or duplicated response leaves the corresponding original score in place. Use `refine_with_details` to inspect candidate, accepted and changed score counts and detect invalid or partial responses. Numeric scores or numeric strings directly keyed by ATC code and a single nested `probability` field are accepted, including a JSON object surrounded by prose or a closed thinking block. The reference tuple format is not parsed. A valid JSON response with no accepted scores has status `no_updates`. Medication codes must be nonempty strings; all-digit codes are rejected in batched mode to avoid index ambiguity. The example reports these counts without printing patient prompts.

The reference uses diagnosis Jaccard similarity, top three training visits, a 0.3 to 0.7 boundary and DDI evidence among boundary candidates. This implementation defaults to a half-open boundary `[0.3, 0.7)`, as in the reference refinement script; set `upper_inclusive=True` to follow the paper’s closed interval. The prompt uses shared clinical guidance across modes, while its compact wording, code/index keyed JSON output, candidate ordering and displayed precision differ from the reference name-based tuple format. Budgeted prompts also differ in layout and may omit supporting evidence. The reference also filters retrieved drug evidence with MEDI and NDC/RxCUI mappings, with a previous-visit rescue. `MediEvidenceFilter.from_reference_files` prepares the filter from MEDI.csv, NDC-to-RxCUI and RxCUI-to-ATC files, a clinical ingredient cache, and a MIMIC-III or MIMIC-IV prescription table, indexing training visits only. The example requires `--ndc-rxcui` and `--ndc-atc` for task labels. Add `--medi` and `--ingredient-cache` to enable the evidence filter; otherwise the example reports that the filter is disabled. These source files must be obtained or prepared separately. The example uses the reference NDC-to-RxCUI-to-ATC3 mapping for both task labels and MEDI index keys. The reference keeps the first ATC entry for each RxCUI, and the example excludes NDCs without a mapping; it reports raw prescription-row coverage. `DrugRecommendationMIMIC3(ndc_to_atc3=...)` selects this explicit mapping, while the task default remains the PyHealth CrossMap. Missing keys are reported separately from missing ingredients and MEDI indication mismatches; history rescue takes precedence. The external RxCUI ingredient cache is incomplete, so missing ingredients can still suppress valid evidence. A DDI prompt is not a hard constraint.

The demo's cached PyHealth NDC-to-ATC mapping also contains an over-broad entry: NDC `60258000601` maps to 133 ATC codes across 52 ATC3 labels. Its external RxCUI is a non-current proprietary placeholder without a reliable ingredient mapping. Earlier demo results using that mapping may have inflated the label vocabulary and should not be compared directly with results using the reference mapping. The example now uses the reference chain and excludes NDCs it cannot map; this avoids the known erroneous entry but does not repair PyHealth’s shared mapping resource.

PyHealth's split-aware task processing fits input processors on training patients, but its label processor adds labels found in held-out data; a benchmark intended to avoid that vocabulary exposure should provide a prespecified medication vocabulary. Reproducing the paper additionally requires its cohort construction, train/validation/test splits, medication vocabulary, mappings, model checkpoints, LLM setup and evaluation protocol. The example uses a freshly trained PyHealth model and does not claim numerical parity.

The example uses a 0.5 decision threshold and averages visit metrics within each patient, then across patients, as in the released script. The DDI rate pools medication pairs across visits. The example records a per-visit `refinement_error` and retains backbone scores if prompt construction or generation fails; the printed error should be investigated before interpreting aggregate metrics. The reference generation defaults to temperature 0.6 and 4096 new tokens, while the paper reports temperature 0.7 and a 4096-token input limit. For a selected model or supplied prompt tokenizer, the example fits prompts to 4,096 input tokens by default using the tokenizer and a 256-token reserve for provider formatting. The OpenRouter adapter raises an error if the provider reports a prompt above that limit; the example retains the backbone scores for that visit and continues. The paper and released script use different generation settings; configure and document them for experiments.

The public [MEDI-C download](https://www.vumc.org/wei-lab/medi) contains the columns used by the filter and is distributed under CC BY-NC-SA 3.0; obtain it separately and check its terms for your use. The reference ingredient cache is in the [GiantMed repository](https://github.com/lvhangkenn/GiantMed/tree/main/data/raw/MIMIC-III). The NDC-to-RxCUI and RxCUI-to-ATC files used for the demo check were `data/ndc2rxnorm_mapping.txt` and `data/ndc2atc_level4.csv` from [GAMENet](https://github.com/sjy1203/GAMENet/tree/master/data); these are external mappings and may differ from the authors' original versions.

Set `--epochs` to a positive integer to train SafeDrug longer. The example does not select a checkpoint by validation metric or use early stopping; it evaluates the final epoch. It reports added and removed predictions against recorded medication labels, pooled by visit; recorded medications are not a direct measure of clinical necessity.

For small hardware, `--max-test-visits` and `--max-new-tokens` limit a smoke run, and `--boundary-low` and `--boundary-high` can narrow the candidate set. Changing the boundary changes the method configuration and does not reproduce the paper. `--save-responses PATH` writes raw model responses locally for parsing diagnostics; responses can contain patient information and should be stored accordingly.

To use an OpenRouter model in the example, set `OPENROUTER_API_KEY` in your environment and pass `--openrouter-model qwen/qwen3-14b`. This transmits the current visit, prior medication history and retrieved training-visit evidence in each prompt to OpenRouter and its selected provider; check the dataset terms and provider's data handling before using it with real records. Do not put the key in command-line arguments or output files. API availability, routing and charges depend on the account and provider.

The input budget preserves the current visit and every candidate code and score. If necessary, it assigns fixed shares of remaining space to candidate names, interaction pairs, similar visits and medication history. Unused shares are not redistributed. Interaction pairs are ordered by candidate scores. Candidates are numbered rows of code, score and name; interactions use those row numbers in an adjacency list. Overlapping diagnoses and procedures use the codes already described in the current-visit section. Counts of retained and total names, history visits, similar visits and interaction pairs are printed for every visit. This ordering is a practical approximation and is not an interaction severity ranking; missing names or DDI pairs can materially change the model’s decisions. If the current visit and candidate scores alone exceed the budget, prompt construction fails rather than silently truncating them. The example reports a refinement error, retains the backbone scores for that visit and continues. Supply `--prompt-tokenizer` for an OpenRouter model other than Qwen3-14B. Provider chat formatting can differ from the local tokenizer; verify reported usage.

### Using PyHealth LLM backends

GiantMed takes a `generate(prompt) -> str` callable; it does not require a particular provider. `HuggingFaceGiantMedGenerator` adapts a loaded causal model and tokenizer. The example's `OpenRouterGenerator` is a separate HTTP adapter used by `--openrouter-model`, not a shared PyHealth backend.

PyHealth's `autoimprove` backends, including `OpenAILLM`, `ClaudeLLM` and `GeminiLLM`, instead accept `llm(system, prompt) -> str`. A wrapper can adapt one to GiantMed. For example, with an OpenAI-compatible server already running locally and the optional `openai>=1.45` package installed:

```python
from pyhealth.autoimprove import OpenAILLM

backend = OpenAILLM(model="your-model", base_url="http://localhost:8000/v1")

def generate(prompt):
    return backend("Return the requested JSON response.", prompt)

# Pass generate=generate when constructing GiantMed.
```

The wrapper sends a system message in addition to GiantMed's rendered prompt. It is not equivalent to the example's OpenRouter adapter, which sends a user message and configures temperature, top-p and reasoning settings. `OpenAILLM` returns text only; it does not expose the provider usage or enforce the example's provider-reported input-token limit. Configure an appropriate prompt token counter and budget on GiantMed separately, and assess provider-specific generation behavior before comparing results. Custom backends may raise errors; the example scripts catch per-visit refinement errors and retain the backbone scores, while other callers should define their own error handling.

The AutoImprove proposer normally sends experiment metadata and aggregate results, whereas a GiantMed prompt may contain patient and retrieved-visit information. A backend does not change the sensitivity of its input: use remote services only when the data terms and provider's handling permit it. `LLMEHREncoder` produces embeddings, and DearLLM's example scores conditional perplexities; their model interfaces serve different purposes from GiantMed's text-generation callable.

### Candidate batching

With a tokenizer and input budget, pass `--candidate-batch-size 32` to refine at most 32 target drugs per request. Each request includes the current visit, every target's code, score and available name, plus the code, score and available name of each boundary drug that interacts with a target. Its indexed interaction list includes **all** boundary interaction pairs involving those targets, including cross-batch pairs. Context drugs are not updated by that request; each drug is updated only in its own target batch. Planning fails before generation if even one target and its complete interaction context cannot fit. The returned `prompt_budget` reports unique DDI coverage, cross-batch pairs, name resolution, per-request token counts and retained history and retrieved visits. `prompts` and `responses` contain all batch calls; the legacy `prompt` and `response` fields contain the first call. Batched responses use zero-based target row numbers as string keys; target ATC codes are also accepted, while out-of-batch and ambiguous duplicate updates are rejected. Indexed responses must contain the complete canonical set of target indices, with no extra numeric keys. Otherwise indexed scores fall back to the backbone because partial or one-based indices cannot be mapped reliably; unambiguous code-keyed scores can still be accepted.

Batching is an adaptation: the paper and reference use one prompt per visit. The batches are refined independently, so interaction evidence is not a hard constraint and independently produced decisions can still conflict. Similar visits are fitted before medication history in each batch; either may be truncated to fit. Each additional request can increase latency and API cost. If a response omits a target or returns an invalid score, the backbone score is retained for that target.

For OpenRouter debugging, `--response-trace PATH` writes each response incrementally as JSONL; this may include clinical information and must be stored accordingly.

### Prompt templates and optional tracking

`GiantMed(..., prompt_template="Assess {boundary} conservatively and consider interactions.")` replaces the shared clinical instruction text. The template must be a nonempty single line containing only the `{boundary}` placeholder; use doubled braces for literal braces. All prompt modes still add their own evidence sections and JSON response contract, and token budgeting includes the template. Custom instructions can conflict with the remaining prompt or change model behavior; evaluate them rather than assuming equivalent safety or paper fidelity. `model.prompt_metadata()` returns the exact patient-independent template, its SHA-256 and a renderer-version identifier. The example accepts the same text from `--prompt-template-file PATH`.

Tracking is disabled by default and does not require MLflow. To write one end-of-run local JSON manifest, pass `--tracking local --tracking-dir PATH`. To use MLflow, install it separately and pass `--tracking mlflow --tracking-uri URI`; set `--experiment-name NAME` if desired. A local MLflow file-store URI can be used for a local-only experiment, subject to your MLflow version's store support. MLflow errors fail visibly by default. To explicitly permit fallback, also pass `--tracking-fallback --tracking-dir PATH`; the console and manifest report that the actual backend is local, the error type and any partial MLflow run ID. A partial remote run may already exist; an attempted failed termination is reported. Local manifests use restrictive file permissions and unique names.

The example records only caller-selected run settings, template text and hash, model-source hash, aggregate evaluation/coverage counts and available provider usage. It does not automatically record rendered prompts, raw responses, patient IDs or individual visit data. **Supply a patient-independent template:** the tracker does not redact patient data or secrets from custom templates or caller-supplied metadata. The existing `--save-responses` and `--response-trace` options separately write raw responses and may contain patient information. Tracking occurs after evaluation; it does not currently record epoch metrics, model weights, dataset snapshots, exact provider routing, or interrupted runs. Store or version those separately as appropriate. Renderer version and source hash are provenance aids, not a guarantee of reproducibility. The patient-specific prompt is not hashed or logged by this feature.

### MIMIC-IV demo and MEDI diagnosis codes

The same workflow can run on the open [MIMIC-IV Clinical Database Demo v2.2](https://physionet.org/content/mimic-iv-demo/2.2/). Download its `hosp` and `icu` tables, and provide the same reference mapping and MEDI files described above:

```sh
python examples/drug_recommendation/giantmed_mimic4.py --root /path/to/mimic-iv-demo --ndc-rxcui /path/to/ndc2rxnorm_mapping.txt --ndc-atc /path/to/ndc2atc_level4.csv --medi /path/to/MEDI.csv --ingredient-cache /path/to/ingredients.json --demo-refinement --max-test-visits 5
```

`--demo-refinement` is an offline, deterministic fake response, useful only to test the pipeline. Omit it for a no-op response, or choose an actual local or remote model using the options described above. Remote providers receive the clinical prompt; check the dataset's terms and provider before using one. The MIMIC-IV example sends diagnosis and procedure codes without resolved names; medication names are resolved when available. The demo requires the configured patients, admissions, ICU stays, diagnoses, procedures and prescriptions tables. Its reference NDC mapping is incomplete; the script reports coverage and excludes unknown NDCs. `DrugRecommendationMIMIC4(ndc_to_atc3=...)` uses the same explicit mapping as the evidence index, while its default remains the PyHealth cross-map.

MIMIC-IV prefixes diagnoses with `9_` or `10_`. MEDI's `ICD9CM` and `ICD10CM` indications are loaded separately and matched only within the same code system after removing dots and normalizing case; no ICD crosswalk is inferred. Unprefixed diagnoses are interpreted as ICD-9-CM for backward compatibility with MIMIC-III. Unknown prefixes are ignored. Exact matching is the default; `ancestor_match=True` optionally accepts a more specific diagnosis with a MEDI code as its prefix, within the same code system. A `missing_indications` outcome means no ingredient has an indication in the query's supported code systems; `no_supported_diagnosis` means the query has no recognized diagnosis codes. Previous-visit history rescue still takes precedence. MEDI coverage and matches are evidence retrieval aids, not validation of clinical appropriateness.
